# Supplementary Note 1 — Reproducibility Guide

This note describes how to reproduce the manuscript's figures and tables from
the `psmc-rs` repository on any machine. All paths are relative to the
repository root; no step depends on the working directory or on paths of the
authors' machines. `experiment/README.md` gives the full details.

## 1) What is packaged and what is regenerated

| item | state in the repository | regenerated by |
| --- | --- | --- |
| Real-data inputs (`experiment/real_data/*.psmcfa`) | packaged | (input data) |
| Simulated inputs (4 models x 500 Mb, S3/S4/S5 inputs) | not packaged (large) | `experiment/scripts/run_main_text.py --steps simulate`, `run_supplementary.py` |
| psmc-rs and C psmc outputs for Figures 2 and 3 (`experiment/runs/{main_text,real_data}/outputs/`) | **not yet packaged**; must be regenerated and committed | `run_main_text.py --steps main`, `run_real_data.py` |
| Runtime and memory tables (Table 2, S3, S4) | packaged (psmc-rs 0.1) | `run_main_text.py --steps perf`, `run_supplementary.py --steps S3,S4` |
| EM-convergence and format-consistency tables (S2, S5) | packaged (psmc-rs 0.1) | `run_supplementary.py --steps S2,S5` |
| Table 1, Figure 3 RMSE table, all figures | packaged | `experiment/run.py` |

Known limitations of the packaged results:

- They were computed with psmc-rs 0.1. psmc-rs 0.2 changes the numerics,
  the input readers, the bootstrap and several defaults (initial
  `rho0 = theta0/4`, the `4+5*3+4` pattern, no smoothing), so every psmc-rs
  result has to be regenerated with 0.2 before publication; the C baseline
  is re-run as well so that both tools start from the same theta/rho ratio
  (`-r4`, psmc-rs `--tr-ratio 4`).
- The inference outputs behind Figures 2 and 3 were never committed (the
  repository's `.gitignore` excluded them). Until they are, `run.py` reports
  them as missing and names the regeneration commands.
- In `S5_format_consistency.csv` the zigzag row is exactly zero in every
  column. This is the expected result, not an artefact. psmc-rs 0.1 read a
  multihetsep or VCF sequence only up to its last heterozygous site, so the
  three S5 inputs of a model differed only in the homozygous 100 bp bins
  after that site, which only the psmcfa held. The zigzag simulation has its
  last heterozygous site in the final bin, so its three inputs are
  identical. The other models drop a few bins (14 for the constant model;
  trimming them from the psmcfa gives byte-identical psmc-rs output).
  psmc-rs 0.2 extends a VCF sequence to its `##contig` length, which
  msprime's VCF writer records, so in a regenerated table the VCF columns
  are zero for every model and only the multihetsep input lacks the
  trailing bins. Regenerated tables record their count per model
  (`psmcfa_bins_after_last_het`), and the caption of Supplementary Figure S2
  should state what S5 measures.
- `S2_em_convergence_trace.csv` includes C psmc's round 0, whose LK of 0 is a
  placeholder (no E-step has run), and Supplementary Figure S1 plots it. A
  regenerated table leaves it out; its row `iter` k holds both tools'
  log-likelihood after k - 1 EM iterations (C's round k, psmc-rs's
  `loglike[k-1]`).
- The human sample (`Papuan_highlands_diploid.psmcfa`) contains chromosome 1
  only (one sequence, 2,487,383 bins of 100 bp) and is labelled accordingly.
- The stdpopsim/msprime versions used for the 0.1 simulations were not
  recorded; the scripts now log them.

## 2) System requirements

- OS: Linux or macOS (Windows via WSL).
- Python >= 3.9. Figures: `numpy`, `pandas`, `matplotlib`. Regenerating
  results additionally: `stdpopsim`, `msprime`, `tskit`, `psutil` (all listed
  in `experiment/requirements.txt`).
- Regenerating results also needs Rust (stable, >= 1.88) and the original C
  psmc (lh3/psmc), built as in section 4.

## 3) Redraw the figures from the packaged results

```bash
git clone https://github.com/larryivan/psmc-rs.git
cd psmc-rs
git checkout <MANUSCRIPT_TAG>

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -U pip
python -m pip install numpy pandas matplotlib

python experiment/run.py
```

`experiment/run.py` uses the interpreter it is started with. It first checks
that the result files and key tables are present and valid, then executes
`experiment/notebooks/all_plots_precomputed.ipynb` headlessly. When results
are missing it lists them grouped by figure, with the command that
regenerates them, and stops; `python experiment/run.py --keep-going` draws the
figures whose inputs are present and exits with status 1.

Other modes:

```bash
python experiment/run.py --skip-plot   # checks only, needs no extra packages
python experiment/run.py --skip-check  # plotting only
```

## 4) Regenerate the results

```bash
python -m pip install -r experiment/requirements.txt

# psmc-rs (used by default from target/release/)
cargo build --release --locked

# Original C psmc; -O1 because an -O2 build segfaults after the first EM round
# on macOS arm64 (Apple clang), while -O0 and -O1 builds agree byte for byte.
git clone https://github.com/lh3/psmc.git /some/dir/psmc
(cd /some/dir/psmc && cc -O1 -o psmc cli.c core.c em.c khmm.c kmin.c main.c aux.c -lm -lz)
export C_PSMC_BIN=/some/dir/psmc/psmc

python experiment/scripts/run_main_text.py      # simulate, Figure 2/Table 1 outputs, Table 2 timings
python experiment/scripts/run_real_data.py      # Figure 3 outputs and fit summary
python experiment/scripts/run_supplementary.py  # Supplementary Tables S2-S5
python experiment/run.py                        # Table 1, all figures
```

Both tools are run with matched settings: 20 EM iterations, `t_max = 15`,
pattern `4+25*2+4+6`, initial theta/rho ratio 4, no psmc-rs smoothing, one
psmc-rs thread. The scripts pass these to psmc-rs explicitly (`--pattern`,
`--t-max`, `--tr-ratio`, `--smooth-lambda 0`, `--mstep-iters 100`), so they
need psmc-rs 0.2; before the first run compared with C psmc they check that
the binary starts from the same ratio and stop if it does not (a 0.1 build
has no `--tr-ratio` and always started from `theta0/5`). Each script logs every command with its wall time and peak
memory to `experiment/runs/<part>/logs/commands.jsonl`. The full regeneration
takes hours and up to about 8 GB of memory (C psmc on 1 Gb in S3); timing
experiments should run on an otherwise idle machine. Commit the regenerated
`experiment/runs/**/outputs/*.json` and `*.psmc` files with the tables (the
S3/S4 timing repeats are ignored by git: they are re-run every time and only
their timings, in the tables, are used).

To spot-check one empirical sample by hand:

```bash
./target/release/psmc-rs experiment/real_data/Papuan_highlands_diploid.psmcfa \
  HomoSapiens.rust.json 20 --pattern '4+25*2+4+6' --t-max 15 --tr-ratio 4 \
  --smooth-lambda 0 --mu 1.25e-8 --threads 1 --no-progress
"$C_PSMC_BIN" -N20 -t15 -r4 -p '4+25*2+4+6' -o HomoSapiens.c.psmc \
  experiment/real_data/Papuan_highlands_diploid.psmcfa
```

## 6) Release archive integrity

Each release archive is published with its SHA-256 checksum in
`<archive>.sha256`. Check a downloaded archive next to it with:

```bash
shasum -a 256 -c psmc-rs-<tag>-<target>.tar.gz.sha256   # or: sha256sum -c ...
```
